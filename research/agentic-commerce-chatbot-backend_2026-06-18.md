# Brainstorm: Agentic Commerce Chatbot — Data-Science Backend

> Generated by Opus brainstorming subagent on 2026-06-18.
> Role scope: **data science team** (backend model + feature serving + AI Gateway). Web team owns frontend integration.

## Framing

The ask is to add an **agentic commerce chatbot** to the PizzaTel storefront: a logged-in customer opens a chat, converses naturally about what they want (including special occasions, holidays, recommendations, and reorders), and the agent assembles a priced order list the customer approves before it flows into the normal order pipeline with a confirmation/tracking link. Text and speech-to-text are both in scope. All model and feature serving must originate from Databricks, and all model access must route through **Databricks AI Gateway**.

**Per the role correction, I am scoping ONLY the data-science backend.** My deliverables are: the Databricks Agent (Agents SDK — `ResponsesAgent`/`ChatAgent` logged to MLflow and deployed to Model Serving), the **tools** that agent exposes, the **feature/context contracts** it consumes, and the **AI Gateway** configuration that fronts every model call. The web team owns the chat widget, mic capture, auth/session, and rendering. My contract surface to them is: one agent serving endpoint (request/response schema) plus the auth model — mirroring exactly how we handed off `synth_qsr-recommender`.

**What already exists in this repo that I build on (not rebuild):**
- `synth_qsr-recommender` Model Serving endpoint — basket-aware recommendations, documented contract (`docs/api.md`). `product_id == str(menu_item_id)`, one ID space with the storefront.
- `synth_qsr-customer-features` Feature Serving endpoint + Lakebase-backed online store (`customer_features` PK `profile_id`, `store_features` PK `unit_id`).
- UC tables: `ref.menu_item` (catalog + category/subcategory/price), `ref.item_price` (period pricing), `silver.guest_order` + `order_item` (order history), `silver.guest_profile` (identity/PII with masks), `silver.loyalty_transaction` (tier/points), `ref.local_events` (holidays/events → special-occasion awareness), `ref.weather_conditions`/`demand_risk_forecast`.
- Established deployment discipline: setup job creates billable endpoints, destroy job tears them down; endpoints created via raw REST (`api_client.do`) not the SDK wrapper; `code_paths` bundles `src/` with the model; pin the whole scientific stack.

**Hard constraints:** (1) every LLM call through AI Gateway; (2) all serving on Databricks; (3) no new generator changes; (4) the agent must NOT write orders directly — it produces a *proposed* order; an explicit human approval gates submission ("agentic commerce" with a human-in-the-loop confirmation step); (5) must be fully automatable from zero via setup/destroy jobs (global CLAUDE.md standard).

## Assumptions

Stated explicitly since I'm running non-interactively:

1. **Order submission is owned by the web team's existing order service.** I expose an `order.submit` *tool* but its actual write path is a backend the web team already has (the OTel storefront's checkout). My tool either (a) calls their REST endpoint, or (b) — fallback for the demo — writes a row to a `synth_silver`-adjacent `pending_order` Delta table that the storefront polls. I default to (a) and treat (b) as the demo stand-in. The agent never writes to `silver.guest_order` directly (that's DLT-managed, append-only from the generator).
2. **Speech-to-text is a frontend concern.** The web team captures audio and sends text to my agent. If they want STT served from Databricks too, I expose a *separate* Whisper-style transcription endpoint via AI Gateway, but the chat agent itself is text-in/text-out. I assume frontend STT first, optional Databricks STT endpoint as a stretch.
3. **The chat LLM is an external/foundation model fronted by AI Gateway** (e.g., a Claude or Llama endpoint registered as an AI Gateway route), not a model we train. We own the route config, rate limits, usage tracking, and the agent orchestration — not the base weights.
4. **`profile_id` is the customer key the web team passes** (same key already used for the recommender). Auth/identity resolution (login → `profile_id`) is the web team's job; I receive a trusted `profile_id` in the request and apply UC row-level security via the service principal.
5. **Pricing source of truth is `ref.menu_item` joined to `ref.item_price`** for the current financial period. The agent must price from UC, never hallucinate prices.
6. **Conversation state** is held per-session by the Agents SDK request (the web team passes prior turns in the `messages` array). No new persistent chat store on my side for v1; MLflow Tracing captures transcripts for eval.
7. **One agent serving endpoint** is the entire contract surface to the web team, named `synth_qsr-commerce-agent` (tracks `schema_prefix` like the others).

## Perspectives

- **Web team (my consumer):** wants exactly one endpoint, a stable JSON schema, an auth/principal grant (`CAN_QUERY`), and a deterministic "proposed order" object they can render with approve/reject buttons. They do not want to know about tools, feature lookups, or Gateway internals. This is the same handoff shape as the recommender — they'll expect a contract doc like `docs/api.md`.
- **Data-science / me (owner):** want the tools to be thin, individually testable (the repo's hermetic-pure-function pattern: `scoring.py` vs `recommender_model.py`), and grounded in real UC tables so the agent can't hallucinate menu items or prices. Want MLflow Tracing + agent-evaluation wired from day one.
- **Governance / platform:** every model call must be observable and rate-limited → AI Gateway is non-negotiable and is the choke point for cost, PII redaction, and safety. UC row filters (`filter_by_franchisee`) and column masks (`mask_email`/`mask_phone`) must still apply when the agent reads profile data. The agent's service principal must be scoped so a customer can only ever see their own profile.
- **The customer (end user):** wants a fast, correct, low-friction conversation that ends in a real order. Latency budget matters — chaining LLM → recommender → feature lookup → pricing per turn can be slow. Trust hinges on accurate prices and a clear approval step.
- **Demo/FE narrative (this repo's purpose):** this is a synthetic-data demo platform. The agent is a showcase of "Databricks-served agentic commerce on your own data + your own recommender." Reusing the existing recommender as a *tool the agent calls* is a strong story (composability of serving endpoints).

## Options

### Option A — `ResponsesAgent` on Model Serving, tools = thin Python functions calling existing endpoints/UC (RECOMMENDED)

**Description:** Author a single MLflow `ResponsesAgent` (the current Agents SDK pattern, superseding `ChatAgent`) in `src/agent/commerce_agent.py`. The LLM is reached via an **AI Gateway route** (foundation model endpoint registered as a Gateway external/served route). The agent exposes a fixed tool set, each a thin, hermetically-testable Python function (pure core + serving wrapper, mirroring `scoring.py`/`recommender_model.py`):

- `menu_search(query, category?, daypart?)` → reads `ref.menu_item` (+ `ref.item_price` for current period) via a Databricks SQL warehouse / `spark.sql`. Returns id, name, category, price.
- `get_recommendations(profile_id, store_id, cart_product_ids, ...)` → **calls the existing `synth_qsr-recommender` endpoint** through the SDK/REST. (Endpoint-as-tool; zero rebuild.)
- `get_customer_context(profile_id)` → calls `synth_qsr-customer-features` Feature Serving endpoint for tier/aov/affinities; optionally a small UC read for name/loyalty (with masks applied).
- `get_order_history(profile_id, limit)` → SQL over `silver.guest_order` + `order_item` for "reorder my usual."
- `get_occasion_context(store_id, date?)` → reads `ref.local_events` / `demand_risk_forecast` for holiday/special-occasion awareness ("It's the day before the Super Bowl — want a party bundle?").
- `price_cart(line_items[])` → authoritative price computation from UC (subtotal, tax estimate, total). Deterministic, no LLM.
- `submit_order(profile_id, store_id, approved_line_items[])` → calls the web team's order service (or demo `pending_order` table). **Only callable after explicit approval flag is set** — enforced in code, not by prompt.

Agent returns a structured `proposed_order` object (line items, qty, unit price, subtotal, tax, total, `status: "proposed"`) plus assistant text. Web team renders, customer approves, web team calls back with `approve=true` → agent invokes `submit_order` → returns `confirmation_id` + `tracking_url`.

Deployed to Model Serving as `synth_qsr-commerce-agent`; MLflow Tracing on; built in setup job (`build_commerce_agent` task after `train_recommender`), torn down in destroy. AI Gateway route created in setup (DAB can't manage it → setup-job notebook, per the project automation standard).

**Pros:** Directly reuses the two existing endpoints as tools (composability — the headline demo story). Matches repo conventions exactly (pure-core + wrapper, setup/destroy, raw-REST endpoint mgmt, `code_paths`). `ResponsesAgent` is the current, deployment-blessed Databricks pattern with native tool-calling + tracing. AI Gateway sits cleanly in front of the one LLM route. Single clean contract for the web team.
**Cons:** Per-turn latency if tools chain serially (mitigate: parallel tool calls, scale-to-zero warmup, cache menu in agent artifact like the recommender bakes its menu). Tool-calling reliability needs eval (agent-evaluation skill). Approval state must be carried in the request by the web team (stateless agent).
**Fit:** Strongest. Idiomatic to this repo and to Databricks GA agent tooling.

### Option B — Multi-Agent Supervisor (Agent Bricks MAS) over a Genie Space + Knowledge Assistant

**Description:** Use Agent Bricks: a supervisor routes between a Genie Space (over the UC order/menu tables) and the recommender, with a KA for menu/policy docs. Order assembly handled by the supervisor.

**Pros:** Less custom code; Genie gives natural-language SQL over the catalog "for free"; good for open-ended data questions.
**Cons:** Genie is exploratory NL→SQL, not a deterministic pricing/order-assembly engine — risky for *commerce* (must not misprice or hallucinate a line item). Harder to enforce the hard "no submit without approval" gate. Less control over the exact `proposed_order` contract the web team needs. AI Gateway integration and the custom `submit_order` tool are awkward to bolt onto MAS. Diverges from the recommender-as-tool reuse story.
**Fit:** Good for analytics/Q&A; weak for transactional commerce with strict output contracts.

### Option C — Frontend-orchestrated tools (web team calls LLM + each endpoint directly; no agent)

**Description:** No Databricks agent. Web team calls an AI Gateway chat route directly and hits the recommender/feature/SQL endpoints itself, doing orchestration in their app.

**Pros:** Minimal backend work from me; maximal web-team control.
**Cons:** Violates the role split (orchestration leaks to web team), no single agent contract, no MLflow Tracing/eval on the agent, tool logic duplicated client-side, pricing/approval logic outside governed backend. Doesn't match "use the Agents SDK."
**Fit:** Rejected — contradicts the explicit ask and the ownership boundary.

## Recommendation

**Adopt Option A: a single MLflow `ResponsesAgent` deployed as `synth_qsr-commerce-agent`, with the LLM fronted by an AI Gateway route, exposing seven thin tools — two of which simply call the existing `synth_qsr-recommender` and `synth_qsr-customer-features` endpoints.**

Rationale: it is the only option that (1) honors the "Agents SDK, Databricks-served, AI Gateway for all model access" constraints, (2) reuses what this repo already shipped instead of rebuilding it (recommender + feature serving become *tools*, which is also the most compelling demo narrative), (3) follows every established repo convention (pure-core/serving-wrapper split for testability, setup-job creation + destroy-job teardown, raw-REST endpoint management, `code_paths` bundling, MLflow Tracing), and (4) gives the web team exactly one contract surface — the same handoff shape that already worked for the recommender. Pricing and the approval gate live in deterministic code, not in the prompt, which is essential for a commerce flow.

Concretely, the build plan: new `src/agent/` package (pure tool cores + `commerce_agent.py` `ResponsesAgent`), `src/setup/build_commerce_agent.py` (register LLM as AI Gateway route, log+register agent, create serving endpoint via raw REST, grant `CAN_QUERY` to the web principal), `resources/` wiring into `setup_job.yml` after `train_recommender` + a teardown step in `destroy_notebook.py`, a `docs/` contract doc for the web team (request/response + approval handshake), hermetic tests for every tool core, and MLflow agent-evaluation scorers for tool-selection accuracy.

**Top risks:**
1. **The order-submission boundary.** `submit_order` depends on the web team's order service, which is out of my control and not yet contract-defined here. If it isn't ready, the whole "flows into the order process + confirmation/tracking link" promise stalls. *Mitigation:* define the `submit_order` contract early as a stub returning `confirmation_id`+`tracking_url`, back it with a demo `pending_order` Delta table the storefront can poll, and treat real integration as a separate handshake — exactly how the recommender's `CAN_QUERY` principal was negotiated.
2. **Pricing/governance correctness under conversation.** The agent must always price from `ref.menu_item`+`ref.item_price` and must never leak another customer's profile. *Mitigation:* `price_cart` is pure deterministic code (no LLM in the number path), the agent's service principal is row-filtered by `filter_by_franchisee` with `mask_email`/`mask_phone` enforced, and AI Gateway provides the PII-redaction + rate-limit choke point. Lock this with eval before handoff.

A secondary watch item: per-turn latency from serial tool chaining — mitigate with parallel tool calls, baked-in menu artifact, and scale-to-zero warmup, and measure it as an eval metric.
